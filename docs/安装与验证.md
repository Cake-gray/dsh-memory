- 时间：2026-11-17
- 设备：Android（DSH App 内置引擎）
- DSH 版本：0.2.1-rc.5
- Node：24.22.1
- pnpm：11.28.9
- profile：`android`
- 源码/文档目录：`/storage/emulated/0/好吃文件夹/插件/1/`
- 运行时包目录：`<DSH_HOME>/profiles/android/node_modules/dsh-memory/`

## 一、安装前检查

- 引擎中 `@deepseek-ai/schemastery`、`@deepseek-ai/dsh-tools`、`@deepseek-ai/dsh-llm` 均存在（版本 3.18.5 / 0.2.1-rc.5 / 0.2.1-rc.5），满足包内 peerDependencies 的区间。
- `node:sqlite` 可用：`DatabaseSync`、`StatementSync` 正常，FTS5 也可用（但本插件未使用）。
- profile 的 `pnpm-workspace.yaml` 设置了 `autoInstallPeers: false`、`nodeLinker: hoisted`，因此本地 tgz 安装不会引入第二份 DSH 内核包。

## 三、打包与安装

打包：在临时目录构造 `package/` 前缀，`tar -czf` 生成
`/storage/emulated/0/好吃文件夹/插件/1/dsh-memory-1.0.0.tgz`。

安装（在 profile 目录执行 pnpm，使用引擎自带的 pnpm）：

```sh
cd "$DSH_HOME/profiles/android"
node "<engine>/node_modules/pnpm/bin/pnpm.mjs" add \
  /storage/emulated/0/好吃文件夹/插件/1/dsh-memory-1.0.0.tgz
```

结果：`+ dsh-memory 1.0.0`，退出码 0。变更：

1. `profiles/android/package.json` 的 `dependencies` 增加
   `"dsh-memory": "file:/storage/emulated/0/好吃文件夹/插件/1/dsh-memory-1.0.0.tgz"`；
2. `pnpm-lock.yaml` 增加 `dsh-memory@file:...` 条目及其 sha512；
3. 由脚本把 `"dsh-memory"` 追加到 `dsh.profile.bundles` 数组（手工编辑前已备份原文件到
   `~/backup-profile/package.json.bak`、`pnpm-lock.yaml.bak`、`cordis.patch.yml.bak`）。

## 四、装配验证（不启动 App）

### 4.1 `--dump-config`

```sh
DSH_HOME=<dsh-home> node "<engine>/node_modules/@deepseek-ai/dsh/lib/bin.js" \
  --profile android --dump-config
```

输出末尾包含：

```yaml
# == dsh-memory
- id: dsh-memory
  name: dsh-memory
```

说明 bundle 层已选中、行已插入。stderr 只有一条与本插件无关的既有告警：
`patch: entry "tmux-context" not found`。

### 4.2 `--dump-config-schema`

```sh
node --expose-internals "<engine>/node_modules/@deepseek-ai/dsh/lib/bin.js" \
  --profile android --dump-config-schema
```

该命令会真正安装 profile 的模块解析拦截并导入每个插件模块（用于读取 Config Schema），因此它同时验证了：

- `dsh-memory` 在真实 profile 解析器下能被 import；
- 三个 `@deepseek-ai/*` peer 能被路由到引擎内的同一份实例；
- `Config` 是合法的 Schemastery Schema，并被投影为 `config81`。

`x-cordis.entries` 中本插件对应：

```json
{"path":"/119","id":"dsh-memory","name":"dsh-memory","status":"schema","configRef":"#/$defs/config81"}
```

`status` 为 `schema`（完整），没有针对 `/119` 的诊断。若保留带小数步进的 `step(0.01)`，
这里的 status 会变成 `partial` 并附带“fractional numeric step needs native validation”告警，
因此最终版去掉了该步进，只保留 min/max。

其余诊断均为安装前就存在的条目（`@earendil-works/pi-ai` 缺失、`preset-native`/`preset-codemode`
载体告警），与本插件无关。

## 五、启用与验收

bundle 选择在 DSH 启动时生效，因此**需要完全退出并重新打开 DSH**（新建会话不够）。
重启后按以下清单验收：

1. 扩展/插件页出现「长期记忆」卡片，副标题为中文描述，图标为渐变脑形图标；
2. 进入设置能看到 14 个字段：总开关、库路径、自动召回、召回范围、召回条数、召回门槛、
   召回字符上限、系统提示、默认类型、条数上限、去重、正文上限、默认返回条数、导出目录；
3. 修改任意字段保存后不重启即生效（volatile）；
4. 对话“记住：我周五晚上一般吃火锅，微辣”，应出现 `memory_save` 调用；
5. 新会话问“我周五一般吃什么”，应出现 `memory_search`，或由自动召回直接带入；
6. 输入 `/memory stats` 能看到条数与数据库路径；
7. 输入 `/memory export json` 能在 `<DSH_HOME>/memory/exports/` 看到导出文件；
8. 查看 `memory_stats` 的 `dbPath` 指向 `<DSH_HOME>/memory/memory.sqlite`。

> 说明：本记录写于安装完成、重启之前。重启后的第 1、2 项（扩展卡片与设置表单）由 DSH 的
> 插件页负责渲染；若卡片缺失，请先确认 `dsh.profile.bundles` 仍包含 `dsh-memory`，再重启。

## 六、回滚

1. 在扩展页停用/移除「长期记忆」，或从 `dsh.profile.bundles` 删除 `"dsh-memory"`；
2. 用备份恢复 profile 文件：
   `~/backup-profile/package.json.bak`、`pnpm-lock.yaml.bak`、`cordis.patch.yml.bak`；
3. 重启 DSH。

记忆数据库不去动：它独立存放在 `<DSH_HOME>/memory/`，卸载插件不会删除。
